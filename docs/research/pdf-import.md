# Импорт PDF банковских выписок в kopeika

> **Дата исследования:** 2026-05-09
>
> **Контекст:** в [анализе конкурентов](README.md) зафиксировано, что ни один из 11 исследованных
> приложений не поддерживает импорт PDF-выписок — это **дифференциатор** для kopeika.
> Данный документ исследует, как именно это реализовать.

## Use case

- **Целевые банки (топ-5 РФ):** Тинькофф, Сбер, Райффайзен, Альфа-Банк, ВТБ
- **Частота импорта:** 1-2 раза в месяц (низкая нагрузка — стоимость LLM не критична)
- **Платформа:** PWA (iOS Safari — приоритет)
- **Backend:** готов появиться (DigitalOcean VM, можно поднять Node-сервис)

## Часть 1. Анализ форматов PDF выписок 5 банков

### 1.1 Тинькофф (Т-Банк)

**Структура PDF:**
- Текстовый PDF (не скан), flow-text вёрстка (НЕ таблица)
- Секция «Движение средств за период», маркер окончания — «Пополнения:»
- Колонки: дата+время, дата расчёта, сумма+валюта, описание, последние 4 цифры карты
- Проблемы: операции на 2-5 строк, сумма дублируется (валюта операции + валюта счёта)

**CSV (основной путь):** разделитель `;`, кодировка `cp1251`, 13 колонок:
```
Дата операции;Дата платежа;Номер карты;Статус;Сумма операции;Валюта операции;
Сумма платежа;Валюта платежа;Кэшбэк;Категория;MCC;Описание;Бонусы
```

**Парсеры на GitHub:** PDF-парсеров нет. Для CSV — [ofxstatement-russian](https://github.com/gerasiov/ofxstatement-russian) (27 звёзд, Python), [ofxstatement-ru](https://github.com/senz/ofxstatement-ru) (Python, 2024).

**Альтернативные форматы:** CSV ✅ | Excel ограниченно | OFX статус неясен | API только для юрлиц

**Стабильность:** CSV стабилен. PDF — нет крупных парсеров для отслеживания изменений.

### 1.2 Сбербанк

**Структура PDF:**
- Текстовый PDF, табличная вёрстка (сложная — многострочные записи, переносы страниц)
- Варианты: «Выписка по счёту дебетовой карты» / «кредитной карты» / «платёжному счёту»
- Колонки: дата операции, дата обработки, код авторизации, описание, категория, сумма, остаток
- Сводка в заголовке: остаток, всего списаний, всего пополнений

**CSV/Excel: УБРАНЫ для физлиц.** Сбербанк — единственный банк из пяти, где PDF — единственный формат выгрузки для физических лиц.

**Парсеры на GitHub:**
- [**Sberbank2Excel**](https://github.com/Ev2geny/Sberbank2Excel) — **134 звезды**, Python, pdfminer.six, **активно поддерживается** (последний коммит 2026-04-17), поддерживает **20+ различных форматов** выписок
- [sberbank-pdf-account-statement](https://github.com/szonov/sberbank-pdf-account-statement) — PHP, 1 звезда, только Бизнес Онлайн
- [Конвертер it-prosto.obit.ru](https://it-prosto.obit.ru/tools/sberbank_statement/) — онлайн-сервис

**Стабильность: ФОРМАТ КРАЙНЕ НЕСТАБИЛЕН.** Из issues Sberbank2Excel за последний год:
- `#84` (2026-04): «выписка по дебетовой карте перестала работать»
- `#82` (2026-04): «поменял форму выписки по накопительному счёту»
- `#80` (2026-03): «поменял форму выписки дебетовой карты»
- `#70` (2025-10): «выписка по платёжному счёту — новый формат SBER_PAYMENT_2407»

**Сбербанк меняет вёрстку выписки каждые 3-6 месяцев.** Разным пользователям могут показываться разные форматы одновременно.

### 1.3 Альфа-Банк

**Структура PDF:**
- Текстовый PDF, табличная вёрстка + **SVG-логотипы**, которые ломают стандартные парсеры
- Колонки: номер документа, дата, дебет/кредит, контрагент, назначение платежа

**CSV:** разделитель `;`, кодировка `cp1251`, 8 колонок:
```
Тип счёта;Номер счета;Валюта;Дата операции;Референс проводки;Описание операции;Приход;Расход
```

**Парсеры на GitHub:** PDF-парсеров нет. Для CSV — ofxstatement-russian/ru, [alfabank-ru-csv-analyzer](https://github.com/solodkiy/alfabank-ru-csv-analyzer) (PHP).

**Альтернативные форматы:** CSV ✅ | Excel ✅ | API только для бизнеса

**Стабильность:** CSV стабилен. PDF — SVG-элементы усложняют парсинг.

### 1.4 Райффайзен

**Структура PDF:**
- Текстовый PDF, табличная вёрстка
- Содержание: реквизиты, ФИО, остатки на начало/конец, список операций

**CSV:** разделитель `;`, кодировка `cp1251`, 6 колонок:
```
Дата транзакции;Описание;Валюта операции;Сумма в валюте операции;Валюта счета;Сумма в валюте счета
```

**Парсеры на GitHub:** только [ofxstatement-ru](https://github.com/senz/ofxstatement-ru) (senz, CSV).

**Альтернативные форматы:** CSV ✅ | Excel ✅ | OFX с проблемами | API для бизнеса

**Стабильность:** мало данных, CSV простой и стабильный.

### 1.5 ВТБ

**Структура PDF:**
- Текстовый PDF, табличная вёрстка
- Проблема: в бизнес-выписках ВТБ фальсифицирует расширения файлов (DOCX → RTF)

**CSV:** разделитель `;`, кодировка `cp1251`, сложная многосекционная структура, 9 колонок в секции транзакций, **формат дат ISO `YYYY-MM-DD`** (не DD.MM.YYYY как у остальных):
```
Номер карты;Дата операции;Дата обработки;Сумма операции;Валюта операции;
Сумма в валюте счёта;Валюта счёта;Основание;Статус
```

**Парсеры на GitHub:** PDF-парсеров нет. Для CSV — ofxstatement-russian/ru, [ofxstatement-vtb24](https://github.com/partizand/ofxstatement-vtb24).

**Альтернативные форматы:** CSV ✅ | Excel убран для физлиц | XML ✅ | API для бизнеса

**Стабильность:** CSV стабилен (формат даты ISO — необычно для РФ). Excel убран.

| Банк | Тип PDF | Вёрстка | CSV | Excel | Сложность PDF | PDF-парсер на GitHub |

## Часть 2. Технические подходы к парсингу

### 2.1 Жёсткие парсеры (regex + table extraction)

Подход: извлечение текста из PDF → regex по характерным паттернам банка → структурированные данные.

#### Библиотеки Node.js

| Библиотека | npm загрузки/нед | Звёзды | Размер | Плюсы | Минусы |
|---|---|---|---|---|---|
| [**pdf-parse**](https://www.npmjs.com/package/pdf-parse) | 4M | 187 | ~21 MB | Простейший API, один вызов | Нет координат текста, нет layout, не для браузера |
| [**pdfjs-dist**](https://www.npmjs.com/package/pdfjs-dist) (Mozilla) | 9.7M | 50K+ | ~800 KB min | Координаты текста (x,y), рендеринг, огромное сообщество | Сложный API, большой bundle для PWA |
| [**unpdf**](https://github.com/unjs/unpdf) | 200K | — | Маленький | Работает везде (Node, браузер, Workers, Deno), 0 нативных зависимостей | Менее зрелый |
| [**pdf2json**](https://github.com/modesty/pdf2json) | — | 2.2K | — | Структурированный JSON с координатами, zero dependency | Только Node.js |
| [**pdfreader**](https://github.com/adrienjoly/npm-pdfreader) | — | — | — | Текст с координатами, встроенная поддержка таблиц | Только Node.js, основан на pdf2json |
| [**tabula-js**](https://github.com/ezodude/tabula-js) | — | — | — | Лучшее извлечение таблиц (Tabula) | **Требует Java JDK** — невозможно в PWA |
| [**pdf-table-extractor**](https://www.npmjs.com/package/pdf-table-extractor) | — | — | — | Специализирован на таблицах | Заброшен (10+ лет) |

**Оценка трудозатрат:** 2-5 дней на парсер одного банка + постоянная поддержка при смене формата. Для 5 банков = 2-5 недель.

**Рекомендация:** `unpdf` для серверного парсинга (0 нативных зависимостей, работает в serverless) или `pdf-parse` для простого извлечения текста перед отправкой в LLM.

#### Плюсы
- Бесплатно, без внешних зависимостей
- Точность 99% для поддерживаемых форматов
- Работает без backend (для клиентского подхода)

#### Минусы
- 2-5 дней разработки на банк
- Ломается при смене формата банком (Сбербанк — каждые 3-6 мес.)
- Не масштабируется на новые банки
- Нужны образцы выписок для разработки и тестирования

### 2.2 LLM (Claude API) — универсальный подход

#### Возможности Claude API для PDF

Claude API **нативно принимает PDF файлы** — не нужно конвертировать в текст. Три способа отправки:
1. **Base64:** `source: { type: "base64", media_type: "application/pdf", data: "<base64>" }` — для загрузки с клиента
2. **URL:** `source: { type: "url", url: "https://..." }` — для хранимых файлов
3. **Files API:** загрузка через Files API, ссылка по `file_id` — для повторного использования

Каждая страница конвертируется в изображение + извлекается текст. Claude анализирует и текст, и визуальную структуру (таблицы, границы колонок).

**Structured Outputs:** Claude API поддерживает гарантированное соответствие JSON Schema на уровне inference — 99.9%+ валидности JSON. Идеально для фиксированной схемы транзакций.

#### Лимиты

| Параметр | Лимит |
|---|---|
| Максимальный размер запроса | 32 MB |
| Максимум страниц | 100 (для моделей с 200K контекстом) |
| Токены на страницу | 1 500-3 000 input tokens |

#### Актуальные цены (май 2026)

| Модель | Input | Output | Контекст |
|---|---|---|---|
| **Claude Haiku 4.5** | $1/MTok | $5/MTok | 200K |
| **Claude Sonnet 4.6** | $3/MTok | $15/MTok | 1M |
| **Claude Opus 4.7** | $5/MTok | $25/MTok | 1M |

#### Расчёт стоимости для одного пользователя

Предположения: средняя выписка 10 страниц ≈ 20 000 input + 3 000 output tokens, 2 раза в месяц.

| Модель | Стоимость/выписка | Стоимость/год (24 выписки) |
|---|---|---|
| **Haiku 4.5** | ~$0.036 | **~$0.86** |
| **Sonnet 4.6** | ~$0.108 | **~$2.60** |
| Haiku (50 стр., макс.) | ~$0.15 | ~$3.60 |

**Вывод: менее $1-4 в год на пользователя.** При 1-2 PDF/мес это буквально копейки.

#### Плюсы
- Универсальность — работает с **любым** банком без написания парсеров
- PDF нативно — не нужно конвертировать в текст
- Structured outputs — гарантированный валидный JSON
- Минимальное время на MVP — 2-3 дня
- Стоимость ничтожна при низкой частоте использования

#### Минусы
- **Обязателен backend** — нельзя выставлять API key на клиенте
- Галлюцинации возможны (нужна валидация: сумма ≠ 0, дата в диапазоне)
- Зависимость от внешнего API (доступность, latency)
- Конфиденциальность — данные уходят в Anthropic API

### 2.3 OCR (для сканированных PDF)

#### tesseract.js

- [GitHub](https://github.com/naptha/tesseract.js) — 35 000+ звёзд
- Работает в браузере (WASM), размер: ~2.1 MB core + ~15 MB русские языковые данные
- Точность: 95-99% на чистом печатном тексте, 60-70% на низкокачественных сканах
- Для русского текста WER 3.7-5.8%

#### Когда нужен OCR

**Практически не нужен для нашего use case.** Все 5 банков генерируют цифровые PDF с текстовым слоем через интернет-банк. Сканированные PDF — исключение (старые бумажные выписки).

Кроме того, Claude API уже обрабатывает изображения нативно — для редких сканов можно отправлять страницы как изображения напрямую в Claude без отдельного OCR.

#### Плюсы / Минусы

- ✅ Бесплатно, работает в браузере, офлайн
- ❌ Не нужен для нашего use case (все PDF текстовые)
- ❌ Медленный в браузере (секунды на страницу)
- ❌ Большой download (~17 MB для русского)
- ❌ Низкая точность для чисел и дат в финансовых документах

### 2.5 Гибридный подход (рекомендуется)

```
PDF Upload
    │
    ▼
[Извлечение текста] ─── pdf-parse / unpdf
    │
    ▼
[Определение банка] ─── regex по ключевым словам (ПАО Сбербанк, Т-Банк, ...)
    │
    ├── Известный банк + CSV доступен ──► Предложить загрузить CSV вместо PDF
    │
    ├── Известный банк + жёсткий парсер ──► Парсер ──► Валидация баланса
    │                                                      │
    │                                                  Ошибка? ──► LLM fallback
    │
    └── Неизвестный банк / без парсера ──► LLM (Claude Haiku)
                                              │
                                              ▼
                                    Structured Output (JSON)
```

Модульная архитектура парсеров (по мотивам [bankstatementparser](https://github.com/sebastienrousseau/bankstatementparser)):
```typescript
interface BankParser {
  name: string;
  detect(text: string): boolean;
  parse(text: string): Transaction[];
}
```

Движок перебирает зарегистрированные парсеры → `detect()` → первый совпавший → `parse()`. Если никто не справился → LLM fallback.

**Валидация:** Golden Rule — `начальный_остаток + поступления - списания == конечный_остаток`.

## Часть 3. Реализация для kopeika

### 3.1 Архитектура — 3 варианта

#### Вариант A: чистый клиент (жёсткие парсеры)

```
[PWA] ─── input type=file ──► pdf-parse (в браузере) ──► regex-парсер Тинькофф/Сбер/Альфа
                                                              │
                                                              ▼
                                                        Transaction[]
```

| Параметр | Значение |
|---|---|
| Сложность реализации | L-XL |
| Зависимости | pdfjs-dist (~800 KB в bundle) |
| Точность | 99% для поддерживаемых банков, 0% для остальных |
| Стоимость | $0 |
| Поддержка | Высокая (парсер Сбера нужно обновлять каждые 3-6 мес.) |
| Backend | Не нужен |

**Минусы:** не работает с неподдерживаемыми банками; pdfjs-dist тяжёлый для PWA; парсер Сбера требует постоянной поддержки; нужны образцы выписок для разработки.

#### Вариант B: LLM на backend

```
[PWA] ─── input type=file ──► upload PDF
                                  │
                                  ▼
                          [Backend: Node + Fastify]
                          POST /api/parse-statement
                                  │
                                  ▼
                          [Claude Haiku API]
                          PDF base64 ──► Structured Output
                                  │
                                  ▼
                          Transaction[] (JSON)
                                  │
                                  ▼
                          [PWA] превью ──► подтверждение ──► сохранение в IndexedDB
```

| Параметр | Значение |
|---|---|
| Сложность реализации | **S-M** |
| Зависимости | Backend (Node + Fastify), Anthropic SDK |
| Точность | 95-98% (любой банк) |
| Стоимость | ~$0.86/год на пользователя |
| Поддержка | Минимальная (обновлять промпт при необходимости) |
| Backend | **Обязателен** |

**Минусы:** нужен backend для прокси API key; зависимость от Anthropic API; данные уходят в облако.

#### Вариант C: гибрид (рекомендуется)

```
[PWA] ─── input type=file ──► определение формата файла
                                  │
                        ┌─────────┼─────────┐
                        ▼         ▼         ▼
                      CSV?      Excel?     PDF?
                        │         │         │
                  CSV-парсер  xlsx-парсер   │
                  (клиент)    (клиент)      │
                        │         │         ▼
                        │         │   [определить банк]
                        │         │         │
                        │         │    ┌────┴────┐
                        │         │    ▼         ▼
                        │         │  жёсткий   LLM fallback
                        │         │  парсер    (backend)
                        │         │    │         │
                        └─────────┴────┴─────────┘
                                  │
                                  ▼
                           Transaction[]
                                  │
                                  ▼
                          превью → правки → сохранение
```

| Параметр | Значение |
|---|---|
| Сложность реализации | M-L |
| Зависимости | Backend (для LLM), CSV/XLSX парсеры на клиенте |
| Точность | 99% (CSV) / 95-98% (LLM) |
| Стоимость | $0 для CSV, ~$0.86/год для PDF через LLM |
| Поддержка | Низкая (CSV стабилен) |
| Backend | Частично (только для PDF fallback) |

**Плюсы:** CSV-парсинг покрывает 4 из 5 банков бесплатно и без backend; LLM fallback для Сбера и неизвестных банков; постепенное расширение без переписывания.

### 3.2 Сравнение вариантов

| Критерий | A (клиент) | B (LLM) | C (гибрид) |
|---|---|---|---|
| Время до MVP | 3-5 недель | **2-3 дня** | 1-2 недели |
| Покрытие банков | 3-5 банков | Все | Все |
| Стоимость/год | $0 | $0.86 | $0-0.86 |
| Backend нужен | Нет | Да | Частично |
| Поддержка формата Сбера | Каждые 3-6 мес. | Не нужна | Не нужна (LLM) |
| Оффлайн-работа | Да | Нет | Частично (CSV) |

### 3.3 Рекомендация: Вариант B (LLM) как MVP → эволюция в Вариант C

**Обоснование:**
1. MVP за 2-3 дня — сразу работает со всеми 5 банками
2. Стоимость ничтожна ($0.86/год) при частоте 1-2 PDF/мес
3. Не нужно собирать образцы выписок и писать regex
4. Не нужно поддерживать парсер Сбера при каждой смене формата
5. Backend всё равно нужен для будущих фич (голосовой ввод, LLM-категоризация, синхронизация)
6. CSV-парсеры можно добавить позже (этап PDF-2) для оффлайн-режима

### 3.4 Поэтапный план реализации

#### Этап PDF-1 (MVP): Backend + Claude Haiku
**Срок:** 2-3 дня | **Зависимости:** DigitalOcean VM, Anthropic API key

- Backend: Node + Fastify, эндпоинт `POST /api/parse-statement`
- Принимает PDF (multipart/form-data), отправляет base64 в Claude Haiku
- Промпт с JSON Schema для structured output
- Возвращает `Transaction[]` клиенту
- Клиент: кнопка «Импортировать выписку» на MainScreen
- Превью транзакций → подтверждение → сохранение в IndexedDB
- Валидация: сумма ≠ 0, дата в разумном диапазоне, дедупликация по hash

#### Этап PDF-2: CSV-парсеры на клиенте
**Срок:** 1 неделя | **Зависимости:** нет

- Универсальный CSV-парсер с автоопределением банка по структуре колонок
- Поддержка: Тинькофф (13 кол.), Альфа (8 кол.), Райффайзен (6 кол.), ВТБ (9 кол.)
- Обработка `cp1251` кодировки на клиенте (`TextDecoder`)
- Для CSV — не нужен backend, работает оффлайн
- UX: при загрузке файла определяем формат (PDF vs CSV) → разные пути

#### Этап PDF-3: жёсткий парсер для Тинькофф (если основной банк пользователя)
**Срок:** 2-3 дня | **Зависимости:** образцы выписок

- PDF-парсер Тинькофф через `unpdf` + regex
- Работает на клиенте, без backend
- Экономия на LLM для самого частого банка

#### Этап PDF-4 (при необходимости): OCR fallback
**Срок:** 2-3 дня | **Зависимости:** реальные кейсы сканированных PDF

- Только если пользователи приносят сканированные PDF (маловероятно)
- Claude API уже обрабатывает изображения → отправляем страницы как картинки
- Отдельный tesseract.js не нужен

#### Шаг 1: Точка входа

## Часть 4. Риски и нюансы

### 4.1 Конфиденциальность данных

**Проблема:** банковские выписки содержат финансовые данные пользователя. При использовании Claude API данные отправляются в Anthropic.

**Политика Anthropic (по документации):**
- Данные, отправленные через API, **не используются для обучения моделей** (в отличие от claude.ai)
- Данные хранятся 30 дней для safety monitoring, затем удаляются
- SOC 2 Type II сертификация
- GDPR compliance

**Митигация:**
- Информировать пользователя перед первым импортом: «Для анализа PDF выписка будет отправлена на сервер. Данные не сохраняются и не используются для обучения AI.»
- Опциональный чекбокс «Я согласен с обработкой данных»
- Для параноиков — CSV-парсинг работает полностью на клиенте без отправки данных

### 4.2 Размер PDF и лимиты

**Типичные размеры:**
- 1 месяц, ~30-50 транзакций: 2-5 страниц, ~200 KB
- 3 месяца, ~100-200 транзакций: 10-15 страниц, ~500 KB
- 1 год, ~500+ транзакций: 30-50 страниц, ~2 MB

**Лимиты Claude API:** 100 страниц, 32 MB — достаточно для любой разумной выписки.

**Рекомендация:** ограничить загрузку 10 MB на клиенте (>50 страниц — предложить разбить по месяцам).

### 4.3 Дубликаты транзакций

**Проблема:** пользователь может импортировать тот же PDF дважды или загрузить перекрывающиеся периоды.

**Решение:**
1. **Hash транзакции** — `SHA-256(дата + сумма + описание + банк)` — уникальный идентификатор
2. При импорте — проверка каждой транзакции на существование hash в IndexedDB
3. Найденные дубликаты: показать в превью с пометкой «Уже импортирована» и снять чекбокс
4. Пользователь решает сам — сохранить или пропустить

**Нюанс:** две одинаковые транзакции (одна сумма, одна дата, одно описание) — легитимный кейс. Решение: при совпадении hash + существующей транзакции — пометить как «возможный дубликат», но не блокировать.

### 4.4 Автокатегоризация при импорте

**Синергия с LLM-подходом:** при парсинге через Claude можно сразу запросить категорию для каждой транзакции. Это не стоит дополнительных токенов (информация уже в контексте).

**Промпт (пример):**
```
Извлеки транзакции из этой банковской выписки. Для каждой транзакции определи:
- date (ISO 8601)
- description (как в выписке)
- amount (отрицательный для расходов, положительный для доходов)
- category (одна из: Продукты, Транспорт, Рестораны, Развлечения, Здоровье,
  Одежда, ЖКХ, Связь, Переводы, Зарплата, Подписки, Другое)
```

При CSV-парсинге категоризация берётся из MCC-кода (Тинькофф) или правил по ключевым словам.

### 4.5 iOS PWA — ограничения ввода файлов

**Хорошая новость:** `<input type="file">` работает в iOS Safari PWA (standalone mode). Пользователь может:
- Выбрать файл из «Файлы» (iCloud Drive, локальные файлы)
- Сфотографировать документ (камера)

**File System Access API** — НЕ работает в iOS Safari. Drag-and-drop — НЕ работает в мобильном Safari.

**Рекомендация:** использовать стандартный `<input type="file" accept=".pdf,.csv,.xlsx">`. Это работает на всех платформах. Для десктопа — добавить drag-and-drop зону как enhancement.

### 4.6 Обновления формата банков

**Проблема:** банки (особенно Сбербанк) периодически меняют вёрстку PDF.

**Стратегия:**
- **LLM-подход (вариант B):** устойчив к изменениям формата — Claude понимает визуальную структуру
- **CSV-парсеры:** формат CSV меняется крайне редко (стабильнее PDF)
- **Жёсткие PDF-парсеры:** требуют обновления → мониторинг через автотесты с образцами
- **Мониторинг:** если парсер не может извлечь транзакции или валидация баланса не проходит → fallback на LLM + алерт разработчику

### 4.7 Стратегическое замечание: CSV vs PDF

Исследование показало неожиданный результат: **CSV-импорт важнее PDF-импорта** для 4 из 5 банков. Только Сбербанк убрал CSV для физлиц. Рекомендация:

1. В UI называть фичу «Импорт выписки» (не «Импорт PDF»)
2. Поддерживать CSV + Excel + PDF
3. При загрузке PDF от банка с доступным CSV — предложить: «Для Тинькофф доступен CSV-формат, который обрабатывается быстрее и без интернета. [Как скачать CSV](ссылка)»
